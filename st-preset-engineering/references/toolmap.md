# toolmap.md — 工具契约卡与建工具方法论

> **何时读**：调工具前；`profile.tool_dir` 不可跑或为空、需要新建工具时（**必读**）。
> **通用性标注**：✅=任意预设可用；🔶=可用但输出含实例专属判读；⛔=依赖实例数据，换家族需替换对应部分。
> **工具被拒绝时**先看是不是自己放错位置，不绕过工具。

## 本 skill 的工具层模型

本 skill 只约定**每个工具必须具备的能力契约**（输入 → 判定逻辑 → 输出格式 → 期望输出），不绑定任何具体实现。`profile.tool_dir` 指向的目录里放什么实现由本机决定：可以是一套现成的参考脚本，也可以是本会话按契约卡新建的等价工具。**工具名只出现在命令示例里，任何实现了同一契约的工具都可登记进 `profile.tool_dir` 替换它。**

## 建工具方法论（tool_dir 不可跑时照此办理）

**触发条件**：第 0 步读 profile 时发现 `tool_dir` 为 null、目录不存在、或某张卡的工具跑不通 → 按对应契约卡在本地实现等价工具（Python 3.8+ 纯标准库即可），登记进 profile，再继续流程。哪步要用就建哪步的卡，**不要一次建全套**；依赖该卡的步骤开始前，工具必须已通过卡上标注的自测。

五条纪律（违反任何一条 = 工具不合格，重写）：

1. **实例数据外置**：代码里不出现预设家族名、源目录绝对路径、词表内容——一切经 CLI 参数、profile 或独立数据文件（如词表 JSON）注入。硬编码实例数据的工具换一个预设就作废，等于没写。
2. **只读与写盘纪律**：源预设目录只读；写文件显式 `newline="\n"`（Windows 文本模式曾让"逐字节还原"差 4896 字节）；生成 JSON 用 `ensure_ascii=False`。**Windows 控制台 GBK 编码下，工具输出含 emoji/中文会报 `UnicodeEncodeError` 或变乱码**——在工具入口**同时重配 stdout 与 stderr**（`sys.stdout.reconfigure(encoding="utf-8")` **和** `sys.stderr.reconfigure(encoding="utf-8")`），或调用前设 `PYTHONIOENCODING=utf-8`。**易漏点：只重配了 stdout**——`sys.exit("中文错误信息")` 走 stderr，未重配则被上层脚本捕获时乱码、断言与字符串匹配全部失效（实测：同一条"拒绝写出"报错，人工跑看着正常、被脚本捕获即乱码）。
3. **输出面最小**：工具输出只有结构、计数与化名（`«NAME:NNN|类别»`），**永不输出条目正文**——工具输出可能被贴进报告或 git。
4. **结论可 diff**：输出格式稳定、确定性（同输入两次运行逐字节一致），判定结果落在一行可 grep 的标记上（如 `[verify] OK`）——期望输出本身就是验收断言。
5. **自测先行**：先造最小 fixture（手工写一个 3 条目的小预设 JSON）跑通卡的"自测"项，再上真实预设。真实预设不是测试环境。fixture 须覆盖每个代码分支——实测：落盘正则的反斜杠转义错误在"无脚本"分支不触发、只有"带脚本"分支自测才逮住；手工内联跑正常 ≠ 落盘版正常。

新建的工具在交付说明里逐个声明（工具名 / 对应哪张卡 / 自测是否通过）。

## 卡 1 — 源只读校验（S0）✅

- **契约**：扫描源目录全部 `.json`（**递归含子目录**；源目录用 `--dir` 显式传参）→ 逐文件记录字节数 + sha256 → 与基线清单比对。新增 / 消失 / 哈希变化逐条报告；无差异时输出含 `[verify] OK` 的一行；退出码 0=一致，1=不一致。**也支持 `--files <f1> [f2…]` 单文件/子集清单模式**——当源文件散落在共享目录（如多人共用收录夹）或只处理个别文件时用文件清单，避免 `--dir` 递归越界扫进别人的预设（实测踩过：9 个散落源文件、目录被多人共享）；两种模式分别落各自 manifest。
- **参考命令**：`python 01_source_manifest.py`（首跑用 `--write` 生成基线清单；`--no-names` 使清单可入库，匿名清单与文件按排序索引配对）
- **写盘防护**：清单文件**不得写进被扫描目录**——清单自身会被当成"新增文件"，首跑自测就会踩中（实测发生过）
- **期望**：`[verify] OK — 全部源文件哈希与清单一致`
- **失效判据**：任何不一致 → **停止一切手术**，先查谁改了源
- **时机**：S0（改前改后各一次）；无工具时的降级：对源文件算 sha256（前 16 位）记入 `profile.hash_baseline`，前后各对一次
- **自测**：把源目录任一文件改一个字节后运行 → 必须报哈希不一致；还原后 → 必须 OK

## 卡 2 — 敏感词扫描（S0 判据）✅（词表可换）

- **契约**：读独立词表文件（JSON，schema：`[{"text": "...", "category": "..."}]`，category 枚举 `override / explicit / illegal`）→ 编译匹配模式（忽略大小写、非重叠）→ 对目标文件计数命中。**只输出文件名、命中数、命中词条名**，不输出上下文；对仓库逐文件跑即得"待入库文件命中 0"的判定。起步词表没有现成基准——建一个 30~60 词、按三类别分好的小词表，登记进 profile 并在交付中声明自建。**任意文本文件可扫**：非 JSON（.md/.txt 等）按整文本扫描、区域归 `text`——"待入库文档逐文件命中检查"经常一半是 markdown，只认 JSON 会整批 ERROR（实测踩过：19 件交付文档里 10 份 .md 首跑 ERROR）。
- **参考命令**：`python 04_audit_for_git.py`（读法：**命中列**为准；启发式标记列是描述性用词的粗筛，既有入库文档也带 1）
- **命中判读**：命中分两类——**结构性命中**（identifier / 字段名命中，如 ST 内置槽名 `nsfw`/`jailbreak`——不构成内容敏感信号）与**内容性命中**（正文命中）。先按词条名人工分类，只对内容性命中执行分流；策略判定看内容性命中。**可按区域（content/identifier/extension/key/other）分离结构/内容性命中**——用 `--regions` 类参数让"85 处命中全落 other 区 = 纯结构性"这类结论可复跑（实测：世界书输入 85 命中全落 other；某预设的 nsfw 词按 content/identifier/extension 拆分），替代"靠目测判结构/内容"。
- **期望**：待入库文件（内容性）命中 0；新文件命中 >0 → 化名/脱敏，不许硬交
- **纪律**：敏感判定是词表命中数说了算，**不靠目测**——实测一个通用词能把 32% 内容误判为敏感（教训见 pitfalls L7）
- **自测**：往词表加一个测试词 → 含该词的 fixture 文件命中数应精确 +1

## 卡 3 — 脱敏管线（S0 红线 2 的执行器）✅（词表可换）

- **契约**（五个子命令）：
  - `classify --in <预设> --out <CSV>`：逐条目按词表分类（SAFE / MIXED / OVERRIDE / EXPLICIT），CSV 含原文 → 工具必须拒绝把 CSV 写出敏感目录
  - `apply --in --out --map --public-json`：产隔离档 + 对照表 + PUBLIC 档。敏感正文替换为 `«BLOCK:NNN»` / `«NAME:NNN|类别»` 占位符，**完整保留机器可读骨架**（identifier / prompt_order / 宏与变量名 / XML 标签 / 正则 flags）；PUBLIC 档 = 词表命中 0 = 可外发
  - `verify-structure --src --san --map`：证明"改动完全局限于被映射槽位"——手术后必跑，防误伤骨架
  - `restore --in --map --out`：从脱敏副本逐字节还原（差异定位只报字节偏移，不输出上下文）
  - `explain --in`：诊断哪个词条触发了脱敏；**调词表前必跑**（防过严脱敏，见卡 2 的 32% 教训）
- **写盘纪律**：对照表强制落 gitignore 目录；工具拒绝 = 放错位置，改路径而不是绕过
- **自测**：restore 产物与源文件逐字节 diff 为空；PUBLIC 档过卡 2 扫描命中 0
- **适用**：`sensitive_strategy: "quarantine"` 时 apply/verify-structure/restore 三步可跳过；但 **`classify`/`explain` 两步仍可跑**（它们只读预设 + 词表，不产任何敏感产物）——quarantine 下词表过严的复核走这两步，不是"整卡无路径"。`none` 策略整卡可跳过

## 卡 4 — 管线验收驱动 ✅（可选）

- **契约**：对登记的文件清单依次跑 卡 3 全链（classify → apply → scan → verify-structure → restore）+ 卡 2 污点复核，汇总一行判定。
- **参考命令**：`python 03_p0_pipeline.py [--all]`；期望：`总判定：全部通过 ✅`
- **时机**：动过脱敏管线 / 词表后必跑
- **备注**：只是卡 1–3 的串联器；新环境可先不建，逐卡手跑即可

## 卡 5 — 结构档案（S1 核心）✅

- **契约**：输入**任意预设 JSON**（只读），stdout 输出六节报告——
  - **输入类型门禁**：入口先探测顶层结构——无 `prompts` 键 / `entries` 为 dict（世界书 lorebook v2 特征）→ 打印输入识别提示（顶层键名 + 是何种非预设格式）并**拒绝产出空报告**（实测：世界书输入被卡 5 输出"格式良好但全空"且 exit 0，差点被误读为"空预设"）。预设类的门禁放入口；`prompt_order`/`extensions` 缺失视字段缺失明确提示。
  1. **管道表**：每条目的开关态（以 `prompt_order` 的 `enabled` 为准，`prompts[].enabled` 是失真残留）/ 阶段 / 分组标记 / role / 字数 / 宏操作。**多 order 块逐块输出**；"哪块生效"是推定（通常块最大/含 dummyId 100001 的生效），推定依据写进报告来源标签。**悬空引用对账（stale refs）**：order 中引用了 prompts[] 里不存在的 identifier（热升级改名/换版的典型残留，实测出现过）必须单列输出；on= 列区分 orphan（在 prompts 不在 order）与 stale（在 order 不在 prompts）两向，孤儿表与之构成双向对账。**另标注两类装配形态**（不随内联顺序流动，改顺序不影响注入点）：
     - **绝对注入条目**（`injection_position=1`）：按 `injection_depth` 注入聊天记录（来源 `openai.js:1219-1224/1305`），标记其 enabled@生效块 + depth + inj_order；
     - **自定义 `sp=true` 条目**（`system_prompt=true` 且 identifier 非内置槽名）：相对装配有过滤路径（`openai.js:1214`），需人工核查。
     （实测：多个预设存在绝对注入条目（部分 ON、depth=2）、部分预设带 `agent*` sp=true 条目——首版档案漏这两维，补丁后收录。）
  2. **槽位表**：setvar/addvar 写入者 vs getvar 读取者（只写不读 = 死槽；同槽多写入者 = 时序地雷）。**"读"的判定范围 = 条目正文 + 脚本 + 正则三处**；世界书/角色卡不在范围内，未覆盖要在报告声明。新增常见 flag 判读：**NO_STATIC_WRITER**（条目/脚本/正则三处写者计数 0）= 该槽可能由运行时手动 `/setvar` 或外部注入写入——判读模板："静态写者为零（同族其余槽均有写者）→ 推定运行时写入，待用户确认"。**可疑槽名标记**：槽名含正则元字符（`[` `]` `*` `(` `\` 等）的打 `#可疑（疑正则语法残留）` 标并单列计数——超大脚本的文本模板常被误抽成槽名（实测）。**外部源提示**：扩展内检测到外部源/主机声明键（`*source_worldbook`、`*_entries`、`*_in_host`、`database_companion` 等模式）时，加一行固定提示——"本预设声明外部源，死槽结论限于条目/脚本/正则三面"（实测：35 死槽与外部世界书声明并存，无提示会把外部消费读成死槽）
  3. **分组表**：按 `profile.group_notation` 的记号 × 阶段聚类，各组 ON 数。**单成员组不算组语义**（多为装饰性前缀），输出时标注"命名约定（结构事实）"。**记号体系无关**：任何具体的记号写法（❗❔🔒 等）只是示例，真实预设可能用完全不同的体系（成对边界条目、emoji+分类名、成员名内嵌标注"（选一）"）——工具不得内置任何记号到语义的映射，一切以 profile 为准；profile 未登记时降级"只列事实"，语义问用户
  4. **孤儿表**：在 prompts[] 不在 order 的条目。"功能性/垃圾"二分在大规模孤儿（>10 条）下不可判定时，改用三线索分簇：名字语义 / 是否被槽引用 / 字符数。**"数据容器型条目"与功能孤儿区分**：孤儿里字符数异常大、内容为序列化 JSON 的（如 `SPreset配置` 类条目 = extensions.SPreset 的逐字节拷贝）→ 标注"容器候选（数据副本，非功能条目）"，给出**不应接回**警示（接回会把整份配置原文注入请求）——只标不猜，语义仍问用户（实测：某孤儿为 18460 字符的 JSON 容器，人工识别）。
  5. **正则表**：各正则的 flags；`markdownOnly=false` 且 `promptOnly=false` 且未禁用 → 标 error（双 False 禁令，见 red-lines 规则 5）。**拷贝层对账**：存在多层（原生 + 绑定层/容器层）时，除逐层清单外必须输出对账行——以原生层为基准：`仅原生名单 / 仅拷贝层名单 / 同名字段差（find/repl 长度、flags）`。"清单分开列"不等于"对账"（实测：两层不同步——仅原生 8、仅拷贝层 2、同名 find 长度 30 vs 54——全靠临时手工对比才拿到）
  6. **脚本表**：脚本与远程 URL 清单（外链 = 风险，按 red-lines 规则 8 分级）；顶层参数（连接绑定字段标注，见 red-lines 规则 6 的准确表述）。**injectScript 提取契约**：参数区按**括号配平**提取（单参正则在嵌套调用处会被右括号截断漏 URL）；**多调用全量列出**（只显第一个 = 静默丢失）；显示截断必须显式标注
- **参考命令**：`python p1_evidence.py report --preset <任意预设.json>`；多版本漂移：对相邻版本各跑档案再 diff（参考实现另有 `--target` / `drift` 子命令，其版本名单是实例数据 ⛔）
- **读法**：autopsy.md §1；六项对账判据见 verification.md L1
- **已知限度**：分组判读依赖记号 + 阶段标记——陌生记号体系下**只列事实不给判定**，降级为参考，语义问用户，不猜测
- **纪律**：宏提取只输出"操作 + 变量名"，正文永不输出（同方法论第 3 条）
- **自测**：对手工 fixture 跑六节计数逐一断言——fixture 至少 5 条目：1 常开 + 互斥组 ×2 成员 + 1 孤儿 + 1 双 False 正则（含嵌套参数与多调用的 injectScript 样本各一）。**另加三类新样本**：1 个绝对注入条目（injection_position=1）断言被标记、1 个自定义 sp=true 条目断言被列出、1 个无 prompts 键的世界书形态输入断言触发输入识别门禁而非空报告。**再补四类新样本**：1 条悬空引用（order 引用不存在的 identifier）断言进入悬空引用清单、1 条同名成对边界断言 toggle 关闭（后文不再归属该区）、1 个拷贝层样本（含仅原生/仅拷贝层/同名差异各一）断言对账行输出、1 个含正则元字符的槽名断言打可疑标。

## 卡 6 — 分组注册表自检 ⛔（registry 是实例数据）

- **契约**：分组注册表（JSON）与卡 5 报告 §3 逐组对账，输出 `自检 PASS：N 组…` 或逐组差异。
- **参考命令**：`python p5_groups_build.py --check`（只验不写；不带 `--check` 会重写文件）
- **通用场景**：换预设家族**不复用**旧 registry——用 profile.model_branches + 组互斥语义替代，或按新家族自建 registry 后再自检
- **自测**：把 fixture 注册表里某组 ON 数改错 → 必须报 FAIL

## 卡 7 — 离线装配（S2-B2 / S5-L2）🔶

- **契约**：
  - `assemble`：读 PUBLIC 档 → 按 prompt_order 顺序、启用态、阶段标记与角色语义复刻酒馆装配 → 输出逐条消息序列（JSON），供改前改后逐消息 diff。不展开宏（占位符原样保留，diff 前按 surgery.md 归一化 `«BLOCK:X»`）
  - `check`：对回复文本跑模板断言（字数区间 / 标签字面 / 选项枚举）
- **参考命令**：`python p5_agent_eval.py assemble --config default --pub <PUBLIC档> --tag <名> --out-dir <仓库外目录>`；`check <回复.txt> --template <已登记模板名> --turn N`
- **通用性**：`assemble` ✅ 任意 PUBLIC 档；`check` ⛔ **模板是实例专属**，且只适用**标签型思维链**渠道——reasoning 通道模型（响应含 reasoning_content）的输出别用它打分（truth-sources.md 的通道警告）
- **诚实标注**：每次输出标"**离线近似**"——它复刻装配语义但由工具实现，与酒馆真值的差异（消息合并 / 运行时增补 / 连接字段处理）要心里有数
- **自测**：同输入连跑两次逐字节一致（确定性）；翻转一个开关后 assemble 输出恰好差预期那条消息

## 卡 8 — mock 端点（S2-B1 请求侧真值）✅

- **契约**：仅监听 `127.0.0.1` 的 OpenAI 兼容最小 mock——`GET /v1/models` 返回单模型；`POST /v1/chat/completions` 把请求体**全量落盘** dump（含 stream=true 的 SSE），另写一份"安全摘要"（消息条数 / 角色序列 / prefill 有无与长度 / model / stream，**不含正文**）；对每次请求返回固定回复
- **参考命令**：`python p2_mock_llm.py --port 9999`
- **配套**：酒馆 → Custom (OpenAI-compatible) → `http://127.0.0.1:9999/v1` + 任意 key + 模型名任意 → 连接 → 发消息 → 读 dump
- **纪律**：dump 落仓库外临时目录；临时聊天，用后零残留
- **证明范围**：装配层；**不等于用户实跑时模型所见**（脚本层会改写请求历史，见 truth-sources.md）
- **自测**：发一条请求后 dump 文件存在且 messages 完整；meta 摘要里 grep 不到任何条目正文
- **降级**：任何能"回显请求体到本地文件"的 OpenAI 兼容 mock 均可——上面两点（全量落盘 + 不含正文的安全摘要）是唯一硬要求

## 卡 9 — 引用扫描（S3 三方一致 / S4 改名删条目前的 UI 引用检查）✅

- **契约**：输入预设 JSON（只读）+ 目标字面量清单（条目名 / identifier / 组号）→ 在**脚本正文、正则 pattern/replaceString、条目正文**三类消费方中搜索每个字面量 → 输出"字面量 → 消费方位置"清单（化名对）。判定标注分两级：
  - `(id)` 命中 = identifier 精确匹配（ASCII 词边界）——**逐条核实后才能当真引用**；内置槽名（'main'/'nsfw'/'scenario'…，清单见 autopsy §6）与纯数字/≤2 字符短名默认高假阳性，抽查即知（实测：短名命中 6 例全假——CSS 数值 / `$1` 反向引用 / JS 属性 / 模块 id）
  - `(name)` 命中 = 条目名字面量——同一规则，短通用词必误报
- **大目标集输出**：支持 `--hits-only`（只列命中 + 总汇行）——实测 431 目标里 429 行"0 命中"是纯噪声，压读表成本
- **计数口径**：`contracts` 标签矩阵的字面量计数为子串计数——前缀包含会重复计数（`think` 的计数含 `thinking`），输出须注明该口径（或按最长匹配拆分）
- **假阳性判据**：命中要能解释为**对该条目的消费语义**才算真引用。排除：语言关键字 / CSS 数值 / 正则反向引用（`$N`）/ 脚本自身的标识符与模块 id / 标准槽词。
- **假阴性盲区（与 `contracts` 契约矩阵联动）**：标签字面量若以 alternation 写法出现（如 `<(thinking|suggestions|disclaimer)>`），`</?tag>` 形提取不识别 → 契约矩阵误报"单方"。矩阵判"单方"的标签，一律补一次**定向子串核查**（在另两侧搜裸词子串）再下结论（实测：`<(thinking|suggestions|disclaimer)>` 被判"单方"实为两方，靠定向子串补证）。
- **参考命令**：`python p1_evidence.py refscan --preset <预设.json>`（参考实现含 `contracts` 子命令输出标签契约矩阵）
- **期望**：每个 UI 脚本引用的条目名/组号都能在此清单里找到消费位置；找不到 = 该引用是孤儿（改名/删除前的风险项）
- **时机**：S3 契约扫描（三方一致）；S4 改名/删条目前（heavy 档必跑）
- **自测**：fixture 里脚本正文含某条目名 → 必须命中该条目；不含消费方的条目 → 0 命中
